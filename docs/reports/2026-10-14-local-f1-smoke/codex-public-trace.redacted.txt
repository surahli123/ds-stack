# ds-mode

You own the number and the inference. A number that passes every check but answers the wrong question, or tells the wrong story, is still wrong. A wrong number stated with confidence is worse than "can't tell".

A data scientist will review your readout, and should be able to check it in under 10 minutes. So every number you report carries a tag that a script resolves to the logged query or check behind it.

## Method

This is a draft, to be replaced with the analyst's own first moves.

1. Restate the question in one sentence and name the decision it feeds. Treat the requester's guess about the cause as one alternative, not the premise.
2. Pin the metric before you query: numerator, denominator, filters, grain and source table. Take it from `metrics.json` in the overlay directory named by `$DS_OVERLAY_DIR` when the metric is there, and say so. If `$DS_OVERLAY_DIR` is unset or holds no `metrics.json`, there is none: never search the filesystem for one. When it isn't, write your definition into the readout and label it `[guess]`. Never invent a definition silently; a plausible number on the wrong definition is the most common wrong answer, and no check below catches it.
3. Decide whether the question can be answered.
   - If two readings of it give materially different numbers and nothing settles which one is meant, ask before computing. When no one can answer, pick the reading the decision most likely needs, state it in the Answer, and put the other in the caveats.
   - If the data can't answer it (the metric isn't logged, the period hasn't landed), say so up front instead of computing a substitute.
4. Check the data before the question. Make sure every period you use is complete (`completeness`). After any join, compare row counts before and after (`fanout`). When a dashboard or other trusted source shows the same metric, reconcile one number against it and record the result in Provenance.
5. Size, then decompose.
   - When a rate moved, run `mix_shift` on the segments whose mix could have shifted (platform, country, traffic source). Use the finest grain that keeps about 100 units per cell on both sides, then rerun at one coarser grain. If the two disagree, report both.
   - For an experiment, run `srm` on the assignment counts before you read any lift.
6. Rule each alternative in or out with evidence. Always consider mix-shift, seasonality and day of week, data completeness, logging or definition changes, and the requester's cause. The evidence names a check or a query result from this session. Label each conclusion measured, inferred or guess.
7. Write the readout below to `readout.md`, run `python3 <dir of this SKILL.md>/tools/verify_readout.py readout.md`, and fix the readout until it passes. Then send the readout as your final reply.

## Queries

Run every query as `python3 <dir of this SKILL.md>/tools/query.py "<SQL>" --as-of <last complete period>`. It enforces the safety envelope (scratch-only writes, one statement, aggregates only, a time cap), prints the result with an id such as `q3`, and logs the statement and result to `.ds-queries.log`. Don't query the data any other way. If a result had to be computed elsewhere, for example by a person, log it with `--pasted --sql ... --columns ... --rows ...` so it gets an id. On a live warehouse, the overlay's adapter takes the place of the SQLite default, with the same log.

## Checks

Run each check as `python3 <dir of this SKILL.md>/checks/run.py <check> --json '<spec>'`. `--list` shows when to use each check and an example spec. Checks take aggregates you computed, never raw rows. Add `"from": "q<n>"` (or a list) to the spec, naming the queries the aggregates came from. Each check prints a JSON line with an id such as `mix_shift#1` and logs it to `.ds-checks.log`.

| Check | Run it when |
|---|---|
| `completeness` | before reporting any period |
| `fanout` | after any join |
| `mix_shift` | a rate moved and segment mix could have changed |
| `srm` | before reading any experiment lift |

Statuses mean different things:

- `pass`: nothing found.
- `flag` is a finding, not a defect. From `mix_shift`, it means segment mix explains a real part of the move, so the Answer must say how much of the change is mix and how much is within-segment change.
- `fail` is a data or query defect. It must change the answer, or the readout must show with evidence why it doesn't. If you can't resolve it, the headline is `can't tell`; say what is missing and what would settle it.
- `could not run` because of how you called it (wrong spec, wrong grain): fix the call and rerun.
- `could not run` because the data can't support the check at all (for example, `completeness` with no earlier periods): answer anyway, report the check as could not run, and put the gap in the caveats. Abstain only if that gap could plausibly change the answer.

Report every check that applies, with its status. If you skip one, say why. Copy check output exactly; never edit it.

## Readout

Your final reply is exactly this format, written for the person who acts on it:

```
## Answer
Headline: <signed number> <unit> (<95% interval>) [q<n> | check:<name>#<n>]   or   Headline: can't tell
<one plain sentence: what happened and how big> [q<n> | check:<name>#<n>]

## What it means for <the decision>
<one or two sentences that compare the interval with the smallest change that would alter the decision> [q<n> | check:<name>#<n>] [given]

## Why we believe it
- Alternatives considered:
  - <alternative>: ruled <in|out> by <evidence> [q<n> | check:<name>#<n>] [measured|inferred|guess]
- Checks run:
  - <check>: <pass|flag|fail|could not run|skipped> <one-line result or reason> [check:<name>#<n>]

## Caveats, and what would change the answer
- <short list>

## Provenance
- Metric: <definition>, from <metrics.json | stated here [guess]>
- Data: <tables or views>, through <last complete period>
- Reconciled: <metric> vs <dashboard or source>, delta <x> [q<n>]   or   Reconciled: not done (<reason>)
- Queries and checks: <where they are logged>
```

- Every line in the Answer, What it means and Why we believe it sections that states a number carries a tag: `[q<n>]` for a logged query, `[check:<name>#<n>]` for a logged check, `[given]` for a number stated in the request, such as a threshold. One bracket can hold several: `[q3, q4]`. A number you can't tag doesn't belong in the readout.
- In Provenance, the logs are `.ds-queries.log` and `.ds-checks.log`, and a last line `- Verified: <the verify_readout.py result line, exactly as printed>` shows the reviewer the trace check passed.
- The interval is required. `mix_shift` reports one for the overall change (`delta_ci95_pp`). For an experiment lift, use a two-proportion interval. When no interval can be computed, write `(no interval: <reason>)`.
- Use causal words ("caused", "drove", "because of") only for a randomized test or a design that identifies the cause. Otherwise say "coincided with" or "is associated with", and name what would confirm it.
- A design that can't identify the cause (a 100% rollout, no holdout) is not a reason to abstain. Headline the measured change, say what it coincided with, and name what would identify the cause. `can't tell` is for when the data can't support the number itself.
- measured means computed from data in this session.
- inferred means it follows from measured facts by reasoning.
- guess means neither.

When this readout grows into a document for other people (a readout, memo, plan or handover), write it with the `ds-doc` skill.

# Review checklist

What a reviewer verifies in a ds-mode readout, in order. The reviewer is a person or a fresh-context subagent that sees the request, the readout and the logs, not the analyst's reasoning. Every item is a yes/no question. Cheap, mechanical items come first, so a review fits in under 10 minutes.

## 1. Do the numbers resolve?

Run `tools/verify_readout.py` on the readout and its logs before reading anything else.

- Does every number carry a tag, and does each tag resolve to a logged query `[q<n>]`, a logged check `[check:<name>#<n>]`, or the request `[given]`?
- Does each tagged query compute what its sentence says (filter, period, grain)?

If this fails, send it back now. Nothing below means anything for a number nobody can trace.

## 2. Is it the right metric?

- Does the Provenance definition (numerator, denominator, filters, grain, source table) match the source of truth, or is it labeled `[guess]`?
- Does the reconciliation line tie the base number to a known figure, with any gap explained?
- If the metric is a proxy for what the decision cares about, does the readout say so?

## 3. Is it the question that was asked?

- Does the restated question match the request, no narrower and no broader, and is the decision named?
- If the request had two readings, did the analyst ask, or state the reading used and put the other in the caveats?

## 4. Do the alternatives rule things in or out?

- Are the standing alternatives all there: mix-shift, seasonality and day of week, data completeness, logging or definition changes, and the requester's cause?
- Would each piece of evidence look different if its alternative were true? A check that can't see the alternative doesn't rule it out.
- Could something else that changed at the same time (a launch, a pricing change, a tracking change) explain the move, and is it addressed?
- Are the comparison windows the same length, the same weekdays and complete, and were they fixed before the results were seen?
- Are segments defined the same way on both sides, and did a coarser grain agree with the finer one?

## 5. Did the right checks run, and did their statuses land?

- Did every applicable check run: `completeness` for each period, `fanout` after each join, `mix_shift` for a moved rate, `srm` before an experiment lift? Is each skipped one explained?
- Does each check line match the logged output exactly?
- Does each `fail` change the answer, or does the readout show with evidence why not? If it can't be resolved, is the headline `can't tell`?
- Does each `flag` show up in the Answer as how much of the move is mix and how much is within-segment?

## 6. Does causal language match the design?

- Do "caused", "drove" and "because of" appear only for a randomized test or a design that identifies the cause?
- Otherwise, does the text say "coincided with" or "is associated with" and name what would confirm it?
- Were treated units chosen by something other than the outcome being measured?

## 7. Is the interval compared with the threshold?

- Is there a 95% interval, or `(no interval: <reason>)` with a reason that holds?
- Does the decision section compare the interval with the smallest change that would alter the decision?
- If the interval spans that threshold, does the readout say `can't tell` or name the uncertainty, not call it from the point estimate?
- Is the sample large enough for the effect size that matters?

## 8. Would a caveat change the answer?

- Is each listed caveat followed by what would settle it?
- Is any missing: a sample that doesn't represent the population the decision covers, an unverified definition, an incomplete period?

## When an item fails

Send the readout back with the item number and the question that failed. Don't fix it yourself or patch the number silently: the analyst owns the number, and a quiet fix hides how it went wrong. Review again from item 1 after the fix. If a wrong number had already reached a reader, log it in the wrong-number archive (see `mistake-classes.md`).

"""Is the period you are about to report fully loaded?

Compares the target period's row count with the median of earlier periods.
Daily ISO dates are compared with the same weekday (the last `baseline_periods`
same-weekday days, default 4), so a normal Saturday isn't read as a partial
load. With under three weeks of history it falls back to the trailing 7 days
and says so. Any other period labels use the trailing `baseline_periods`
(default 7).
Fails when the target is missing, below `min_ratio` of that median (default
0.9: late or partial data), or above `max_ratio` when given (double loads).
"""

import statistics
from datetime import date

from _common import COULD_NOT_RUN, FAIL, PASS, Result, SpecError, require

NAME = "completeness"
DEFAULT_MIN_RATIO = 0.9
MIN_BASELINE = 3


def _as_date(label):
    try:
        return date.fromisoformat(label)
    except ValueError:
        return None


def run(spec):
    try:
        series = require(spec, "series", list)
        target = require(spec, "target", str)
        min_ratio = float(spec.get("min_ratio", DEFAULT_MIN_RATIO))
        max_ratio = spec.get("max_ratio")
        max_ratio = None if max_ratio is None else float(max_ratio)
        rows = {}
        for point in series:
            period = require(point, "period", str)
            if period in rows:
                raise SpecError(f"period '{period}' appears twice")
            rows[period] = require(point, "rows", int)
    except (SpecError, TypeError, ValueError) as err:
        return Result(NAME, COULD_NOT_RUN, f"could not run: {err}")

    dates = {p: _as_date(p) for p in list(rows) + [target]}
    daily = all(dates.values())
    if daily:
        prior = sorted((p for p in rows if dates[p] < dates[target]), key=dates.get)
        earlier, basis = [], "trailing days"
        if spec.get("same_weekday", True):

            basis = "trailing days" if basis == "trailing days" else "trailing days (under 3 weeks of same-weekday history)"

        earlier = sorted(p for p in rows if p < target)[-k:]
        basis = "trailing periods"
    if len(earlier) < MIN_BASELINE:
        return Result(NAME, COULD_NOT_RUN,
                      f"could not run: need at least {MIN_BASELINE} earlier periods ({basis}) before {target}, got {len(earlier)}")

               "min_ratio": min_ratio, "max_ratio": max_ratio}
    if target not in rows:
        return Result(NAME, FAIL, f"{target} has no rows loaded", details)
    if baseline == 0:
        return Result(NAME, COULD_NOT_RUN, "could not run: baseline median is 0 rows", details)

    ratio = rows[target] / baseline
    details.update(target_rows=rows[target], ratio=round(ratio, 4))

"""Split a rate change into within-segment (rate) and segment-mix effects.

Kitagawa decomposition with midpoint weights, so the two effects sum exactly to
the overall change:

    delta = sum_s (r_after - r_before) * (w_after + w_before) / 2       # rate effect
          + sum_s (w_after - w_before) * ((r_after + r_before) / 2 - r)  # mix effect

where r is the midpoint of the overall rates. Subtracting r leaves the total
unchanged (the weight changes sum to zero) and makes each segment's mix term
readable: a segment adds to the drop only if its share grew and its rate is
below average, or its share shrank and its rate is above average.

Returns "flag" (a finding the answer must report, not a data defect) when mix
accounts for at least `threshold` of the movement, measured as
|mix| / (|mix| + |rate|) so offsetting effects (Simpson's paradox) still show,
AND the mix effect is larger than noise: at least `min_effect_pp` and at least
`z` standard errors of the overall change. Standard errors are binomial and
assume independent units; clustered units (sessions within users) make them
too small, so treat the intervals as a lower bound on the uncertainty.
"""

import math

from _common import COULD_NOT_RUN, FLAG, PASS, Result, SpecError, require

NAME = "mix_shift"
DEFAULT_THRESHOLD = 0.3
DEFAULT_MIN_EFFECT_PP = 0.1
DEFAULT_Z = 2.0
Z95 = 1.96


def _counts(segment, side):
    part = segment.get(side)
    if not isinstance(part, dict):
        raise SpecError(f"segment '{segment.get('name')}' is missing '{side}'")
    n = require(part, "n", int)
    k = require(part, "k", int)
    if k > n:
        raise SpecError(f"segment '{segment.get('name')}' {side}: k > n")
    return n, k


def _var(rate, n):
    return rate * (1 - rate) / n


def decompose(segments):
    parsed = []
    for segment in segments:
        name = segment.get("name", f"segment_{len(parsed)}")
        nb, kb = _counts(segment, "before")
        na, ka = _counts(segment, "after")
        if nb == 0 or na == 0:
            raise SpecError(f"segment '{name}' has n = 0 on one side; drop it or merge it")
        parsed.append((name, nb, kb, na, ka))
    total_b = sum(p[1] for p in parsed)
    total_a = sum(p[3] for p in parsed)
    overall_b = sum(p[2] for p in parsed) / total_b
    overall_a = sum(p[4] for p in parsed) / total_a
    midpoint = (overall_a + overall_b) / 2

    rate_effect = mix_effect = rate_var = 0.0
    per_segment = []
    for name, nb, kb, na, ka in parsed:
        wb, wa = nb / total_b, na / total_a
        rb, ra = kb / nb, ka / na
        weight = (wa + wb) / 2
        rate_part = (ra - rb) * weight
        mix_part = (wa - wb) * ((ra + rb) / 2 - midpoint)
        rate_effect += rate_part
        mix_effect += mix_part
        rate_var += weight ** 2 * (_var(rb, nb) + _var(ra, na))
        per_segment.append({
            "name": name, "n_before": nb, "n_after": na,
            "weight_before": round(wb, 6), "weight_after": round(wa, 6),
            "rate_before": round(rb, 6), "rate_after": round(ra, 6),
            "rate_effect_pp": round(100 * rate_part, 4), "mix_effect_pp": round(100 * mix_part, 4),
        })
    delta_se = math.sqrt(_var(overall_b, total_b) + _var(overall_a, total_a))
    return {
        "overall_before": overall_b, "overall_after": overall_a, "delta": overall_a - overall_b,
        "delta_se": delta_se, "rate_effect": rate_effect, "rate_effect_se": math.sqrt(rate_var),
        "mix_effect": mix_effect, "segments": per_segment,
        "smallest_segment_n": min(min(p[1], p[3]) for p in parsed),
    }


def _ci_pp(value, se):
    return [round(100 * (value - Z95 * se), 3), round(100 * (value + Z95 * se), 3)]


def run(spec):
    try:
        segments = require(spec, "segments", list)
        if len(segments) < 2:
            raise SpecError("needs at least 2 segments to separate mix from rate")
        threshold = float(spec.get("threshold", DEFAULT_THRESHOLD))
        min_effect_pp = float(spec.get("min_effect_pp", DEFAULT_MIN_EFFECT_PP))
        z = float(spec.get("z", DEFAULT_Z))
        parts = decompose(segments)
    except (SpecError, TypeError, ValueError) as err:
        return Result(NAME, COULD_NOT_RUN, f"could not run: {err}")

    rate, mix, delta = parts["rate_effect"], parts["mix_effect"], parts["delta"]
    moved = abs(rate) + abs(mix)
    share = abs(mix) / moved if moved > 1e-12 else 0.0
    noise_floor = max(min_effect_pp / 100, z * parts["delta_se"])
    details = {
        "overall_before": round(parts["overall_before"], 6),
        "overall_after": round(parts["overall_after"], 6),
        "delta_pp": round(100 * delta, 4),
        "delta_ci95_pp": _ci_pp(delta, parts["delta_se"]),
        "rate_effect_pp": round(100 * rate, 4),
        "rate_effect_ci95_pp": _ci_pp(rate, parts["rate_effect_se"]),
        "mix_effect_pp": round(100 * mix, 4),
        "mix_share": round(share, 4),
        "noise_floor_pp": round(100 * noise_floor, 4),
        "threshold": threshold, "min_effect_pp": min_effect_pp, "z": z,
        "smallest_segment_n": parts["smallest_segment_n"],
        "se_assumes_independent_units": True,
        "segments": parts["segments"],
    }
    lo, hi = details["rate_effect_ci95_pp"]
    summary = (f"overall change {100 * delta:+.2f} pp = within-segment {100 * rate:+.2f} pp "
               f"(95% CI {lo:+.2f} to {hi:+.2f}) + mix {100 * mix:+.2f} pp (mix share {share:.0%})")
    if share >= threshold and abs(mix) >= noise_floor:
        return Result(NAME, FLAG, "mix-dominant: " + summary + "; report the mix shift as part of the answer", details)
    if share >= threshold:
        summary += f"; the mix effect is within noise (floor {100 * noise_floor:.2f} pp)"
    return Result(NAME, PASS, summary, details)

#!/usr/bin/env python3
"""Check that every number in a ds-mode readout traces to a logged query or check.

    python3 tools/verify_readout.py readout.md [--queries .ds-queries.log] [--checks .ds-checks.log]

In the Answer, "What it means" and "Why we believe it" sections:
- every line that states a number carries a tag: [q<n>] for a logged query,
  [check:<name>#<n>] for a logged check, or [given] for a number stated in the
  request (a threshold, a date range). One bracket may hold several: [q3, q4].
- every [q<n>] is a query that ran (through the runner, or pasted with --pasted);
- every [check:<name>#<n>] is a logged check whose "from" names queries that ran.
The Provenance section must have a "Reconciled:" line.

Dates, a "95%" in front of "interval" or "CI", and digits inside names (v2,
q3) don't count as numbers. Logs default to $DS_QUERIES_LOG / $DS_CHECKS_LOG,
else the files in the current directory.

Prints "verify_readout: pass (...)" or "verify_readout: fail" with one line per
problem, then the [given] lines for the reviewer to confirm against the request.
Exit code: 0 pass, 1 fail, 3 usage error.
"""

import argparse
import json
import os
import re
import sys

ONE_TAG = r"(?:q\d+|check:[a-z_]+#\d+|given)"
TAGS = re.compile(r"\[\s*(" + ONE_TAG + r"(?:\s*[,;|]\s*" + ONE_TAG + r")*)\s*\]", re.I)
LABELS = re.compile(r"\[(?:measured|inferred|guess)\]", re.I)
HEADING = re.compile(r"^#{1,4}\s+(.+?)\s*#*\s*$", re.M)
DATE = re.compile(r"\b\d{4}-\d{2}(?:-\d{2})?\b|\b\d{4}-W\d{2}\b", re.I)
CI_LEVEL = re.compile(r"\b(?:80|90|95|99)\s*%\s*(?=(?:confidence\s+)?(?:interval|CI)\b)", re.I)
LIST_MARKER = re.compile(r"^\s*(?:[-*+]|\d+[.)])\s+")
NUMBER = re.compile(r"(?<![A-Za-z_#\d.])[-+−]?\d+(?:[.,]\d+)*")
CHECKED_SECTIONS = ("answer", "what it means", "why we believe")


def _clean(text):
    text = re.sub(r"^```[a-z]*\s*$", "", text, flags=re.M)
    return text.replace("**", "").replace("__", "").replace("`", "")


def sections(text):
    parts = HEADING.split(_clean(text))
    return [(parts[i].strip(), parts[i + 1]) for i in range(1, len(parts) - 1, 2)]


def numbers_in(line):
    body = LIST_MARKER.sub("", TAGS.sub(" ", LABELS.sub(" ", line)))
    body = CI_LEVEL.sub(" ", DATE.sub(" ", body))
    return NUMBER.findall(body)


def tags_in(line):
    found = []
    for group in TAGS.findall(line):
        found += [tag.strip().lower() for tag in re.split(r"[,;|]", group) if tag.strip()]
    return found


def read_jsonl(path):
    entries = []
    try:
        with open(path) as handle:
            for line in handle:
                try:
                    entries.append(json.loads(line))
                except ValueError:
                    continue
    except FileNotFoundError:
        pass
    return entries


def verify(text, queries, checks):
    """Return (problems, stats, given_lines)."""
    ran = {e["id"].lower() for e in queries if e.get("id") and e.get("status") == "ok"}
    tried = {e["id"].lower(): e.get("status") for e in queries if e.get("id")}
    logged_checks = {e["id"].lower(): e for e in checks if e.get("id")}
    problems, given, stats = [], [], {"lines": 0, "numbers": 0, "queries": set(), "checks": set()}
    found = sections(text)
    if not any(name.lower().startswith("answer") for name, _ in found):
        problems.append("no Answer section")
    for name, body in found:
        lowered = name.lower()
        if lowered.startswith("provenance") and not re.search(r"^\s*[-*]?\s*reconciled\s*:", body, re.I | re.M):
            problems.append("Provenance has no 'Reconciled:' line (write 'Reconciled: not done (<reason>)' if none was possible)")
        if not lowered.startswith(CHECKED_SECTIONS):
            continue
        for line in body.splitlines():
            numbers, tags = numbers_in(line), tags_in(line)
            if numbers:
                stats["lines"] += 1
                stats["numbers"] += len(numbers)
                if not tags:
                    problems.append(f"untagged number in '{name}': {line.strip()}")
            for tag in tags:
                if tag == "given":
                    given.append(line.strip())
                elif tag.startswith("q"):
                    stats["queries"].add(tag)
                    if tag not in ran:
                        why = f"it was {tried[tag]}" if tag in tried else "it is not in the query log"
                        problems.append(f"[{tag}] doesn't resolve: {why}")
                else:
                    check_id = tag.split(":", 1)[1]
                    stats["checks"].add(check_id)
                    entry = logged_checks.get(check_id)
                    if entry is None:
                        problems.append(f"[{tag}] doesn't resolve: it is not in the check log")
                    elif not entry.get("from"):
                        problems.append(f"[{tag}] has no source query: rerun it with \"from\": \"q<n>\" in the spec")
                    else:
                        missing = [q for q in entry["from"] if q.lower() not in ran]
                        if missing:
                            problems.append(f"[{tag}] names queries that didn't run: {', '.join(missing)}")
    return list(dict.fromkeys(problems)), stats, given


def main(argv=None):
    parser = argparse.ArgumentParser(description=__doc__, formatter_class=argparse.RawDescriptionHelpFormatter)
    parser.add_argument("readout", help="the readout file (use - for stdin)")
    parser.add_argument("--queries", default=os.environ.get("DS_QUERIES_LOG") or ".ds-queries.log")
    parser.add_argument("--checks", default=os.environ.get("DS_CHECKS_LOG") or ".ds-checks.log")
    args = parser.parse_args(argv)
    try:
        text = sys.stdin.read() if args.readout == "-" else open(args.readout).read()
    except OSError as err:
        print(f"verify_readout: can't read the readout ({err})", file=sys.stderr)
        return 3
    problems, stats, given = verify(text, read_jsonl(args.queries), read_jsonl(args.checks))
    counts = (f"{stats['numbers']} numbers on {stats['lines']} lines; {len(stats['queries'])} queries, "
              f"{len(stats['checks'])} checks, {len(given)} given")
    if problems:
        print(f"verify_readout: fail ({counts})")
        for problem in problems:
            print(f"  - {problem}")
    else:
        print(f"verify_readout: pass ({counts})")
    for line in given:
        print(f"  given (confirm against the request): {line}")
    return 1 if problems else 0


if __name__ == "__main__":
    sys.exit(main())
