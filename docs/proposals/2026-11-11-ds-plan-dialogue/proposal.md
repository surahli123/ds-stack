# 让 ds-plan 支持逐步讨论的修改提案

日期：2026 年 11 月 11 日
状态：待审阅提案，包含完整候选文本和 diff；没有修改已安装或仓库中的正式 skill

## 建议与预期影响

**建议修改现有 `ds-plan`，让它按请求选择逐步讨论或一次性计划审查，再修正 `ds-mode` 的入口。**不用再增加一个职责重叠的 `ds-brainstorm`。保留现有指标定义、查询记录、机械检查、readout 和文档技能。

这次要解决的核心问题是：用户还在定义研究对象与比较方式时，agent 太快交出一份看似严谨的完整计划。新增更多 tenant、P80 或 causal inference 条款不足以解决这个交互问题；需要允许问题在几轮有效讨论中形成，并验证用户纠正后后续推理确实变化。

候选方案可改善这个已确认的流程冲突，**尚未通过新的模型行为实验，也没有复现公司电脑上的原失败会话**。本提案不宣称修复已经生效。

## 本轮确认的剩余问题

### 1 触发词承诺 brainstorm 正文却禁止所需交互

[当前 ds-plan](base/skills/ds-plan/SKILL.md:4) 的 description 会在 brainstorm 请求上触发；但第 14 行要求：

> in one pass, in writing. No multi-round Socratic loop, no web search, no subagents.

第 19 行又把询问限制为最多两题，无法回答就标记 `[guess]` 然后继续。这与本次用户明确需要的“逐步形成定义、解释提问用途、发现盲区”存在直接冲突。

**已确认的是规范冲突。**不能据此推断所有模型都会失败，也不能说每次分析都应该长谈。更合适的改动是区分逐步讨论与明确请求一版计划，而非把单轮检查完全删除。

### 2 新的路由仍可能漏掉已结束随机实验中的概念问题

[当前 ds-mode 第 1 步](base/skills/ds-mode/SKILL.md:22) 的前置规划例子是新指标、没有随机实验的因果问题、昂贵决策。一个已有随机实验、指标也已存在，但 power user 尚未定义的问题，仍可能被当成可以直接计算的常规分析。

这是条件文字可见的缺口；尚未用运行时 trace 证明真实路由必然遗漏。候选修改将“研究问题、人群或比较方式未定”列为直接条件，同时复用已经讨论清楚的计划，避免重复采访。

### 3 两轮计划评测没有测到渐进讨论 正确结尾也不能证明正文已纠偏

[当前 runner](base/eval/plan/run_plan.py:84) 的第一轮要求保存完整 plan.md，并只回复一行；第 90 行要求第二轮用短段落回应异议，再重复 closing lines。任务在一开始已经提供随机化、历史数据字段和时间范围。这个场景适合检查计划输出与一次异议，不会让用户逐步补充事实或共同定义概念。

[当前 grader](base/eval/plan/grade_plan.py:33) 读取每个结尾键的最后一个值，第 41 至 48 行以关键词判分。它不比较正文与 closing lines 的一致性，也不能判断是否真的回应异议。

本轮运行了 [可重复探针](probe_current_grader.py)，使用固定 main 的真实 scorer 和 gold，结果见 [完整输入与输出](grader-probe-results.json)：

| 构造输入 | 当前 scorer 得分 |
| --- | --- |
| 正文与结尾一致的合理计划 | 1.0 |
| 正文要求按 tenant 平均并按实验期行为分组，结尾写正确的 user 和 pre-test 关键词 | 1.0 |
| 正文直接忽略异议，结尾仍填正确关键词 | 1.0 |
| 在需要澄清时，先讨论定义而不填写完整结尾字段 | 0.0 |

这证明了 scorer 的覆盖边界，**不是模型生成过这些错误正文的证据**。它也没有执行整个 runner 的污染或退出状态检查。现有 scorer 可以继续用于字段回归，但不能作为“已经学会 brainstorm”的验收标准。

### 4 实验单位的纠错条款需要避免成为另一个默认答案

新版已针对原案例写入 user、tenant 和处理前属性规则。这有帮助，但 [当前第 31 行](base/skills/ds-plan/SKILL.md:31) 把目标对象、聚合方式和推断要求压在同一句绝对规则里，容易让模型在下一例中照搬答案。

候选文本改为分别确认目标人群、权重、结果表示和真实处理分配；不知道的配置需要查证。同一个用户可能经历两臂时，应明确当前处理定义还不能直接套用。提案不指定一套适用于所有实验的聚类或统计算法，也不默认用户一定随机化。

## 候选根因与还不能确定的部分

当前最有证据的设计解释是：**skill 把问题形成当成一次性计划检查，入口和评测又偏向快速生成完整计划，因此允许一份方向未校准的计划过早完成。**明确禁止多轮、最多两问后猜定、强制计划式结尾，共同支持这个解释。

竞争解释仍包括模型本身的领域误判、长会话遗忘用户纠正、额外运行时指令，以及公司环境的实际安装版本不同。单纯删除“禁止多轮”不保证这些问题一起消失。要把设计解释升级成行为层面的因果结论，需要在相同设置下比较当前 main 与候选稿，而不是只读文本。

## 具体改动提案

| 改动 | 期望解决的问题 | 限制 |
| --- | --- | --- |
| ds-plan 按请求选择逐步讨论或一次性计划审查 | 让模糊定义可以讨论，明确请求可以直接完成 | 不要求每个任务固定问几轮 |
| 维护简短的已定范围 已接受选择与未知项 | 避免从 3p power 漂到整体 search 或重复打开 P80 | 不新增持久化状态系统，也不每轮打印模板 |
| 回答当前问题后 仅在有用时追问一题并解释用途 | 减少用户不知道为什么被问及旁支问题的情况 | 不是强制每轮提问 |
| 把用户纠正落实到后续定义与比较 | 让反驳改变推理，而非只改变最后一行 | 仍允许说明为何某个反驳不改变计划 |
| 区分业务选择与待数据核查的事实 | 不再因不知道阈值天数而无限讨论，也不猜定随机化 | 缺失事实影响的方法步骤保持条件表达 |
| 设置明确的总结与交接标准 | 能回答 brainstorm 是否完成，并交给数据工作 | 不把该标准变成额外审批流程 |
| ds-mode 第 1 步按未定人群与比较方式路由 | 让已有随机实验中的概念问题也能进入 ds-plan | 已讨论完的计划直接复用 |

研究对象仍可按用户要求保持 user-level，但具体处理定义和推断须服从真实设计。P80、零点击、新激活等案例用于行为验证，避免把这一个实验的固定答案写成所有任务的必经流程。

### 为什么不单独新增 ds-brainstorm

当前 `ds-plan` 的触发已经包含 brainstorm。新增另一个 skill 会带来入口重叠，还需要解释两者谁先运行。先在现有 skill 中支持两种交互方式，改动范围较小。

如果后续行为评测显示同一 skill 无法稳定区分两种请求，再考虑拆分。只追加 tenant 或 power 规则虽然最短，但不会解决多轮禁令与过早结束的问题，因此不推荐。

## 如何验证以及何时才可以宣布有效

先保留现有 p2 作为计划输出回归，再使用能逐步透露事实的多轮场景，检查是否真的保持研究对象、回答当前问题、根据异议修改后续推理，并在定义形成后及时交接。

真实 3p 案例已经参与 prompt 设计，属于开发材料。需要未用于调试的其他任务来验证能否迁移。对“问题问得是否有用”“正文是否承认并应用了用户纠正”等语义判断，先由人工按具体回合记录证据；不能靠末尾三个关键词代替。

成本比较应覆盖整段讨论的 token、时长、重复问题和到达可确认方案的累计成本，同时保留明确问题一次完成的对照。计划多写或少写几行不等于 brainstorm 更有效。具体设置与判据应在运行前固定；本轮没有发起模型实验或额外代理评审。
