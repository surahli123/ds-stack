# 验证讨论过程而不只检查计划结尾

状态：拟议的行为验收设计，尚未运行新的模型实验。这里的案例与判据属于评测材料，不能放入模型正在执行的 skill，也不能在运行时暴露预期答案。

## 保留已有评测的用途

保留当前 p2 的两轮计划评测与 grader，用于回归检查 user-level 目标、历史行为分组和回应异议的基本字段。它不能单独验收逐步 brainstorm，也不能验证正文与结尾是否一致。本提案不改原 pass_rule，不把本次构造输入的探针算作模型实验。

## 开发案例与独立验证

真实 3p 案例已经用于发现缺口和撰写提案，因此只能算开发案例；复述这段对话不能证明泛化。候选修改、当前 main 和 plain prompting 应在相同的模型设置、工具权限和用户事实下比较。任何模型、设置和额外评审调用都须在执行时按用户授权选定，本提案不默认发起新 agent。

### A 真实案例走查

这是一组关键转折，不是要求 agent 逐字问同一套问题。只在相关时提供事实；不得把尚未告知的用户偏好当成模型理应知道的答案。

| 用户提供的信息或转折 | 应观察的行为 | 明确失败的行为 |
| --- | --- | --- |
| 3p DAU 下降、初步关联 relevance launch、leads 问 power 用户是否更受影响；未定义 power | 保持 3p 用户这一研究范围，指出定义或比较中的关键未决选择，开展必要讨论 | 仅凭 Statsig 指定 tenant 随机化；立刻产出定稿方案并把未知设计写成事实 |
| 用户把结果限定为 3p search 点击，排除系统引用 | 后续定义和比较保留这个口径 | 继续混入 chat/AI 自动引用，或转成整体 search power |
| 用户说多数用户可能只有一次点击 | 区分稀疏主体与高频尾部，提出可用的数据核查或候选定义 | 未看分布就断言不存在有意义的频次组，或要求用户现场提供其没有的数据 |
| 用户纠正“我们只要理解 3p power，当前没有定义” | 停止旁支，解释正在使用的定义以及该定义如何回答问题 | 只写“你说得对”，随后继续讨论整体 1p/3p 使用构成 |
| 用户问“怎么用数学表达” | 先把当前候选用符号说清楚，并解释其业务含义 | 不回答公式，转而提出新的研究议程 |
| 用户提出并接受历史 P80 | 记录为候选；阈值对应多少天、并列和组大小留待数据核查 | 把 P80 说成已验证的 power 定义，或因尚无分位数数值继续无限追问 |
| 用户指出有人实验期才开始点击 3p | 保留处理前身份，把原历史未活跃组的结果包括在内 | 只看实验期点击者，或按处理后行为重分高频/轻度组 |
| 用户补充实验已经结束 | 后续保持 retro 语境，核查原随机记录与 control；不预设其可用 | 把启动新实验作为开展这次 retro 的前置条件 |
| 用户问是否 brainstorm 完成，并要求总结 | 直接说明是否足够进入数据核查；列已定选择、剩余选择与缺失事实 | 再启动一套问卷；把数据检查项全部当成讨论未完成；编造实际效应结果 |

初始信息可有两个版本：一开始就说明 retro；或在中途才补充。两个版本用于检查不同能力，不能当成完全独立的两个业务问题增加任务数。

### B 明确请求一版计划

提供完整随机化单位、历史定义、结果口径、时间窗口和分析目标，明确要求“直接给我一版简短计划”。应在一次答复中完成；不能强制进行 brainstorming，也不能重新询问已给信息。可以复用现有 p2 作为该类回归，而不把它当成新方案增益的主要证据。

### C 更换分配方式与目标对象

用尚未用于修改 prompt 的合成例子：按公司随机推出 CRM 功能，但业务问题问的是销售人员的活动变化。应区分研究对象与分配单位，不能照搬“必须用户随机”或“必须按公司平均”的答案。另设 session 分配的版本，检查同一人可能接触两臂时，是否仍错误构造固定 user T/C。

验收关注识别设计未知点与提出正确的下一步核查，不要求在没有完整数据结构时指定唯一统计实现。

### D 修正一次会影响后续的前提

在讨论使用频率后，用户说明“power 指对这个流程的依赖，并非打开次数多”；或在一个已接受定义后说明历史日志缺失。应明确改动影响哪些假设并更新计划。不得只在最后的 Premises 行补一句 caveat，正文继续用原定义。

### E 合理保留未知与结束讨论

用户无法给出随机化设置或分位数数值，但已确认目标、候选分组、比较和结果。应产出有条件的计划，列出查配置或看分布的检查；不能猜定设计，也不能因缺少数值拒绝总结。反向对照：如果用户尚未决定是在研究频率还是依赖，须如实标记这个实质选择，不能宣称已经完全达成一致。

## 按回合记录判据

每个判定都附模型原文、回合编号和依据，至少检查：

1. 是否保持用户的研究对象和已确认口径。
2. 是否回答当前问题，提出的后续问题是否改变下一步选择。
3. 是否在用户纠正后更新后续推理，而非只补正确关键词。
4. 是否保留已接受定义，正确处理需要重新讨论的新证据。
5. 是否区分缺失事实、业务选择、候选假设与实际结果。
6. 是否在合适的时候总结并交接，且不超出授权范围执行分析。

历史分组、随机化、缺失记录等事实有明确判据时可以机械检查。问题是否有用、是否实际回应异议、正文是否自相矛盾，先由人工按原文判断；若以后使用模型评审，另行校准，不能把关键词命中当成这些语义能力的证明。

## 运行与成本记录

复用当前 runner 的隔离、session resume、transcript、退出状态和成本记录机制；增加由任务定义的回合列表，使中间回合可以是澄清而不是完整 plan.md。只在最后明确要求交付计划，不强制每轮填写 Unit 或 Segment。任务事实、预期答案和评分材料分开。

用户脚本或人工操作只补充已有设定中的事实；对脚本之外但合理的问题，统一回答未知或给出事先定义的事实，并记录。不能根据 arm 的表现临时多给某一组提示。

质量先通过方向保持、纠偏和事实边界的检查，再比较成本：总 token、总时长、重复问题数，以及到“用户能够确认候选方案”的累计成本。单篇计划的字数不是多轮讨论总成本的替代指标；不要求为了与单轮一样短而省掉必要澄清，也不接受无关的长问卷。

小规模开发走查只能报告具体行为与开销，不能宣称总体胜率。保留现有评测对样本量不足的标记；只有在未用于调试的任务和预先确定的判据上完成比较后，才能讨论是否比当前 skill 更有效。
