# Meta prompt: localise the brief and the draft section

You maintain the report `<REPORT_TITLE>`, which audits the MCP-side event data for `<AGENTIC_TOOL>` calls. Three documents come with this prompt. The first is a summary of the context and the decisions already made with the owner. The second is a standing brief that explains what the report is for and how to keep revising it. The third is a draft of a missing section on the inside of the agentic search service, `<AGENTIC_SERVICE>`. All three were written outside this environment, from photos of the report and from public planning documents, and all are kept in a public repository. So they are anonymised on purpose: internal names are replaced by placeholders in angle brackets, and the report's observed numbers are left out. Before you use them, localise them to this project.

**How you receive them.** The owner either pastes the documents below this prompt or gives you their paths (`context-and-decisions.md`, `internal-agent-brief.md` and `service-internal-section-draft.md`, in the same folder as this file). Use whichever you have. If you have both and they differ, the pasted text is the version the owner meant.

**Read the context first, and work within it.** `context-and-decisions.md` records what the owner has already decided, what was tried and dropped, and which questions are still open. Those decisions took a long discussion to reach, and the owner does not want to have it again. Treat the settled points as given and do not reopen them or propose the dropped ideas. If your evidence shows a settled point is wrong, state the evidence once in your final report and carry on.

**Resolve every placeholder from evidence.** The brief and the draft section each start with a Placeholders table that says what each placeholder stands for and where its value is likely to be found. Look for the real value in the existing report, the MCP handler code, the service's code or the data catalogue. For each placeholder, record the value, where you found it (file and line, table, or report section) and how confident you are. If you cannot establish a value from evidence, leave the placeholder in place and list it as unresolved, with what you tried. A gap is better than a guess here: a wrong table or field name does not fail loudly, it quietly sends later analysis to the wrong data, and nobody notices until a number turns out wrong.

**Produce, in this order:**

1. A placeholder mapping table: placeholder, value, where found, confidence.
2. The localised brief. Adopt it as your own standing instructions for every later revision of the report.
3. The localised section, with real names. Fill its "Observed evidence" column by auditing the service's own logs to the same evidence standard as the existing MCP-side tables: row counts or a code read, and the report's status labels. Where the public text states a fact without its value (for example that the service has a run budget), restore the value from the report. Write "not yet audited" only where you truly could not look, and say why.

**Settle three open questions from evidence.** The public documents were written with these unresolved, and the draft section takes a provisional position on each. Investigate each one in the code and the data. For each, say what you found, on what basis (file and line, query, or log sample), and how confident you are. Where your finding differs from the provisional position, update the localised documents and say so in your report. These end in decisions that belong to the owner and the teams, so bring evidence and a recommendation, not a ruling.

1. *Where executed effort and the fallback reason are recorded.* The existing report asks for them on the MCP event row. The draft section makes the service their system of record, on the reasoning that the fallback happens inside the service and only the service knows why. Find where the fallback decision is made, which layer holds the reason at that moment, and what is passed back to the MCP handler (today it reaches only the tool response). Recommend where each should be logged, and if both layers log it, which one is the record. Note what each option needs changed.
2. *Whether light-effort requests pass through the service.* The planning documents assumed that light search is the current search tool and never reaches the service. The existing report suggests instead that `<AGENTIC_TOOL>` carries a requested and an executed effort and can recover to light inside one call. Trace three paths in the code: a call to `<AGENTIC_TOOL>` that asks for light effort, if the tool accepts one; an agentic request that recovers to light; and a call to the current search tool. For each, say whether the service is invoked and whether it leaves a record in `<SERVICE_LOG_SOURCE>`. This decides whether light-tier behaviour can be read from the service's logs or only from MCP-side data, and so which analyses need the MCP data scientist's data.
3. *Who should lead the service-side check of the join key.* The existing report names the MCP side as lead, with the service owner. The draft section proposes the service owner as lead, with the MCP team. Find where `<INVOCATION_ID_FIELD>` is set, whether it is forwarded in the call to the service, and where on the service side it would be read and logged. The side whose code has to change is usually the natural lead. Report what you found and which lead it points to, and leave the choice to the owner.

**Do the work, then raise questions together at the end.** The owner expects output, not a discussion at each step. When something is unclear, choose the reading that fits the settled context, note in one line which reading you chose, and continue. Hold these for your final report rather than stopping for them: placeholders you could not resolve; anything in the brief or the section that contradicts what you find in the code or data; and anything that needs a privacy decision, which you flag and do not build around. Stop early only if nothing useful can be done without an answer, for example if you cannot read the service's logs at all. The brief was written from photos of the report, so it may be wrong in details. Where the evidence and the brief disagree, the evidence wins, and you report the disagreement rather than quietly correcting it.

**Keep the localised versions internal.** They contain internal names and data, so they stay in this environment and are not written back to the public repository the originals came from.

**When you are done, report briefly:** the mapping table; what you audited in the service's logs and how (sources, queries or code read, time window); your findings and recommendations on the three open questions; what remains unresolved; and which statements in the brief turned out to be wrong.
